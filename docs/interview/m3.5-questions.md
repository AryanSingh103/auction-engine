# Milestone 3.5 interview questions

Generated from the M3.5 diff (`git diff c0ead86..HEAD`) by the interview-questions subagent. Answer in your own words, whenever you like (below each question, or in chat); Claude then grades the answers and points out where they are wrong or vague.

## 1. The first apply failed, then fixed itself
*Files: `deploy/terraform/trial/main.tf` (aws_autoscaling_group, aws_launch_template, IAM section)*

On the first real `terraform apply`, the ASG reported an "Authentication Failure" on its first instance launch. The AutoScaling service-linked role had been created about 5 seconds earlier. The ASG retried on its own, and Terraform later replaced the tainted ASG.
- Explain what actually failed, and why Terraform's dependency graph could not have prevented it.
- What does "tainted" mean in Terraform? Why did Terraform replace the ASG, when AWS had already recovered?
- Name two ways to make a first apply into a fresh account deterministic. What does each cost you?
- In M6 this runs from GitHub Actions. How would you tell a transient eventual-consistency error from a real misconfiguration in a CI log, and should the pipeline retry automatically?

## 2. SIGTERM before deregistration
*Files: `deploy/terraform/trial/main.tf` (deregistration_delay, stopTimeout, aws_ecs_service, aws_autoscaling_group); `cmd/api/` (graceful shutdown)*

When the ASG was replaced, the old task received SIGTERM about 26 seconds before ECS deregistered it from the target group. The ASG terminated the instance without ECS draining it first.
- Lay out the intended shutdown sequence, using `deregistration_delay = 15`, `SHUTDOWN_TIMEOUT = 15s` and `stopTimeout = 20`. Then lay out what actually happened. What did clients hitting the ALB see during those 26 seconds?
- Why does your server's graceful drain not protect you in this sequence?
- What mechanisms would make instance termination wait for ECS to drain tasks first? Which would you use in M6, and what does it change about how you scale in or roll the AMI?
- Once the invariants from M4 and M5 exist, is a task killed mid-request a correctness problem or only an availability problem? Name the worst-case request.

## 3. Bridge networking and the ephemeral port range
*Files: `deploy/terraform/trial/main.tf` (security groups, task definition portMappings, metadata_options); `docs/decisions/021-trial-deploy.md`*

The trial uses bridge mode with `hostPort = 0`, a security-group rule open for 32768–65535 from the ALB, and IMDSv2 with a hop limit of 1.
- Why does the ALB-to-instance rule have to span the whole ephemeral range? What else on the instance is now reachable from the ALB's security group?
- Explain how the hop limit stops the container from using the instance role. Is that a real security boundary? What changes if you move to awsvpc, or if the API later needs its own AWS permissions (for example S3 in M6)?
- ADR 021 rejects awsvpc because of the ENI limit on a t4g.small. What is ENI trunking? Would it change that decision for M6, and what would awsvpc give you that bridge cannot?

## 4. Which endpoint the load balancer trusts
*Files: `deploy/terraform/trial/main.tf` (aws_lb_target_group health_check, task definition DATABASE_URL/REDIS_URL, health_check_grace_period_seconds)*

The target group health-checks `/healthz`. `/readyz` returns 503 by design, because `DATABASE_URL` and `REDIS_URL` point at `.invalid` hosts and the pools connect lazily.
- In M6, with a real RDS instance, should the ALB check `/healthz` or `/readyz`? Walk through what happens to every task during a 60-second RDS failover under each choice.
- What does the ECS service's own health handling add on top of the ALB's check? How do `health_check_grace_period_seconds = 10` and the target group thresholds interact during a slow start?
- The trial relies on the pgx pool and the Redis client connecting lazily. Is that behavior something the service should depend on in production? What would you want to happen at startup if the database is unreachable?

## 5. From throwaway to production
*Files: `deploy/terraform/trial/versions.tf`, `deploy/terraform/trial/main.tf` (data.aws_ssm_parameter.ecs_ami, launch_template version, ecr image_tag_mutability, default VPC), `.gitignore`*

The trial uses local state, the default VPC with public IPs on instances, HTTP only, an AMI resolved from SSM at plan time, and `wait_for_steady_state = true`.
- Local state was fine for an hour-long stack. What concretely goes wrong in M6 without a remote backend and state locking, once both CI and your laptop can run `apply`?
- The AMI ID comes from SSM on every plan. What happens to the running instance when AWS publishes a new AMI and you next run `apply`? Is "always the latest" a property you actually want in production?
- `wait_for_steady_state` makes a green apply mean "the deploy worked". What failure modes does it not catch, and what happens to the Terraform run (and the state) when a bad image never becomes healthy?
- List the changes you would make to the network and the edge for M6 (subnets, egress, TLS, how instances reach ECR). For each one, say what you pay for it.
